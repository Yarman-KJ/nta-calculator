# 원문·현행 데이터·작업지침

GitHub 저장소가 실제 기준이다. 기존 배포본 `index.html`에서 코드를 복원했으며 초기 분리 시 출력 바이트가 동일함을 검사한다. `src/index.template.html`의 문서·스타일과 `src/*.js`의 동작, `data/current/project-data.js`의 현행 데이터를 편집하고 `pnpm run build`로 HTML을 재생성한다. 기존 이미지와 공략 경로는 유지한다.

`references/NTA_통합소스_V6.md`와 manifest는 원문 스냅샷이다. 현행 실행 데이터가 V6 전체와 일치하거나 모든 규칙이 실측되었다는 뜻이 아니다. `data/current/evidence.json`은 우선 분리한 대표 쟁점이며 전수 검증표가 아니다. 나머지 기존 데이터의 확정 수준은 아직 감사하지 않았다. 근거는 원문 파일과 고유한 인용 문장으로 찾고, 게임 버전이 없으면 임의로 만들지 않는다.

## 패치 5단계

1. 수집: 새 패치·사용자 정정·측정 자료를 보존하고 날짜·출처·대상·조건·게임 버전을 기록한다.
2. 비교: 저장소 현행값과 차이를 조사하고 `source-evidence`(원문 근거), `user-confirmed`(사용자 확정), `operating-policy`(운영 정책), `unverified`(미확인)를 구별한다. 원문 근거가 있다는 사실과 게임 검증 여부는 별도 축이다. 충돌은 양쪽 근거를 남긴다.
3. 반영: 확인된 범위만 현행 데이터·코드에 최소 변경한다. 미확인은 별도 기록하며 가정이 필요하면 계산의 가정으로 명시한다. V6 원문은 그대로 둔다.
4. 검증: 관련 회귀 테스트와 전체 테스트, HTML 재생성 일치를 확인한다. 통과·실패·미실행을 구분하고 실측하지 않은 게임 규칙을 확정하지 않는다.
5. 보고·승인: 변경점, 근거, 검증 결과, 남은 충돌을 보고한다. 공개 배포·병합은 사용자 승인 뒤 수행한다.

게임 분석이 미완성이어도 이 절차를 적용할 수 있다. 이는 완성 선언이 아니라 새 정보와 불확실성을 누적 관리하는 절차다. 이후 분석으로 기존 가정을 수정하거나 반박하는 것도 정상적인 패치다.

## 검증

`pnpm install --frozen-lockfile` 후 `pnpm test`, `pnpm run check:build`를 실행한다. 기존 로컬 개발 자료의 테스트 6개를 복원해 경로와 jsdom 의존성만 수정했다. 원래 저장소에는 테스트와 CI가 없었다. 구형 상세 계산기의 `test.cjs`는 현재 배포본에 없는 `data.js/engine.js` 대상이므로 옮기지 않았다. 자료의 게임상 정확도, 브라우저 육안 검사, 외부 이미지 가용성은 이 테스트로 보장하지 않는다.
